This rule requires explicit type annotations for empty arrays (`[]`, `new Array()`, `Array()`) in variable declarations, class properties, and object literal properties **only when their element type isn't already known from context**.

> This is a **type-aware** rule. It asks the TypeScript type checker whether each empty array already has a contextual type, so it only flags arrays that are genuinely ambiguous evolving-`any`s.

**Problem:**

TypeScript infers empty arrays as an **"evolving any"** type that evolves as you push elements. TypeScript already prevents unsafe usage, so it's type-safe. The issue is purely about **code clarity**: without an explicit annotation, it's not clear what type the array should contain.

**Solution:**

This rule enforces explicit type annotations for empty arrays for **code clarity and consistency**. It's a style preference, not a safety requirement.

Because the decision is made from the checker's contextual type, an empty array whose type is already known is **never** flagged — including function return positions, contextually-typed arguments, typed array elements, `satisfies` clauses, and deeply nested typed objects.

**Note:** With `noImplicitAny: true` (strict mode), empty arrays without annotations are inferred as `never[]`, which prevents adding any elements. If you intentionally want `never[]`, explicitly type it: `const arr: never[] = []`.

## Examples

<Tabs>
<TabItem value="❌ Incorrect">

```ts
const arr = [];
const items = [];
let data = [];
var list = [];
const more = new Array();
const extra = Array();

class Foo {
  items = [];
  data = new Array();
}

const obj = {
  items: [],
  data: new Array(),
};
```

</TabItem>
<TabItem value="✅ Correct">

```ts
const arr: string[] = [];
const items: number[] = [];
let data: boolean[] = [];
var list: any[] = [];
const more: string[] = new Array();
const extra = new Array<string>();

class Foo {
  items: string[] = [];
  data: number[] = new Array();
}

const obj = {
  items: [] as string[],
  data: new Array<number>(),
};

// If you intentionally want never[], you can be explicit about it
const placeholder: never[] = [];

// Non-empty arrays don't require explicit types
const numbers = [1, 2, 3];
const strings = ['a', 'b'];

// Type assertions are also acceptable
const typedArr = [] as string[];
const typedItems = [] as number[];

interface Config {
  plugins: string[];
}

// Contextually-typed empty arrays are accepted — the element type is already known
const config: Config = { plugins: [] };
function make(): { items: string[] } {
  return { items: [] };
}
const listItems: { items: string[] }[] = [{ items: [] }];
const sat = { items: [] } satisfies { items: string[] };
```

</TabItem>
</Tabs>

## Options

### `ignoreMutableVariables`

When set to `true`, `let` and `var` declarations are ignored. This can be useful if you rely on TypeScript's evolving array type for mutable variables. `const` declarations and class properties are always checked.

<Tabs>
<TabItem value="❌ Incorrect">

```ts option='{ "ignoreMutableVariables": true }'
const arr = [];
```

</TabItem>
<TabItem value="✅ Correct">

```ts option='{ "ignoreMutableVariables": true }'
let arr = [];
var list = [];
const typed: string[] = [];
```

</TabItem>
</Tabs>

## When Not To Use It

If you prefer to rely on TypeScript's evolving any type inference for empty arrays, or if you consistently use type assertions instead of type annotations, you can turn this rule off. Since evolving any is type-safe, this rule is primarily about code clarity and style preference rather than type safety.
